# Idea Validation — <Internal product or new service idea>

> Fill this in **before** an internal product gets build time ([Planning §8.7](../Planning.md#87-validate-before-we-build), rule 28). The aim is to learn, cheaply, whether the problem is real and someone will pay or use it — not to prove the idea is good. Method: **build → measure → learn** (Lean Startup). Owner: the named idea owner; decision: Sponsor.

| Field | Value |
|-------|-------|
| Idea owner (one person) | <name> |
| Time budget for validation | <e.g. 2 weeks, 4 hours a week>; recorded in sprint capacity |
| Decision date | <date> |
| Decision by | Sponsor |

## 1. The problem
- Who has the problem? (a specific group, not "everyone")
- What do they do about it today, and what does it cost them?
- **Riskiest assumption:** the one belief that, if wrong, kills the idea.

## 2. Evidence (collect before building)

| Test | Target | Result |
|------|--------|--------|
| Problem interviews with people in the target group (not friends or the team) | at least **5** | |
| People who show real interest (sign-up, pre-order, letter of intent, agree to a pilot) | <number> | |
| Competitors or alternatives checked (including "do nothing" and tools that add AI to what users already have) | listed | |
| Smallest test that could fail (landing page, clickable prototype, manual "concierge" service) | run | |

## 3. Plan if we go ahead
- MVP scope (one page) and the **one metric** that shows it works
- **Launch and marketing plan:** who will hear about it, through which channel, by when
- Who builds it, and how much sprint capacity it gets (README §6.6 rule 10)
- **Stop criteria:** e.g. "fewer than 10 active users 8 weeks after launch → stop and write the closure report"

## 4. Decision
- [ ] **Go** — becomes an internal product (Gate G1 next)
- [ ] **Change** — new riskiest assumption, one more validation round
- [ ] **Stop** — record the reason and lessons in the knowledge base (Maintenance rule 24)
